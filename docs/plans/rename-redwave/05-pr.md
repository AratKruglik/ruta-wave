## Summary

The app still carried the working name Tunewave. This change renames every identifier to the decided name Redwave (bundle ID `dev.kruhlyk.redwave`, target and product `Redwave`, `RedwaveApp`, Keychain service `dev.kruhlyk.redwave.session`) and removes the stores of the old identifier `dev.kruhlyk.tunewave`, which hold Google session cookies. On first launch, a cleanup in Auth deletes the old Keychain item and the old WebKit, HTTP storage, cache and preference data. The cleanup runs on every launch until it has nothing left to remove. Backlog row 0.3, issue #6, requested by the owner.

## Manual steps after merge

1. Quit any running Tunewave build before first launching Redwave.
2. Delete the old launchable builds. Each one recreates the old stores if launched:
   - `Tunewave.xcodeproj/`
   - `build/.../Tunewave.app`
   - `~/Library/Developer/Xcode/DerivedData/Tunewave-*/Build/Products/Debug/Tunewave.app`
   - `~/Library/Developer/Xcode/DerivedData/Tunewave-*/Build/Products/Release/Tunewave.app`
3. After the first Redwave launch, check:
   - `security find-generic-password -s dev.kruhlyk.tunewave.session` finds nothing.
   - No `dev.kruhlyk.tunewave*` entries remain in `~/Library/HTTPStorages`, `~/Library/WebKit` and `~/Library/Caches`.
   - `ls ~/Library/Cookies | grep -i tunewave` is empty. Run this from a Terminal with Full Disk Access; it could not be checked from the pipeline.
   - Fallback if the Keychain prompt is denied: `security delete-generic-password -s dev.kruhlyk.tunewave.session`.
4. Sign in again and confirm the session survives a relaunch.
5. Revoke the old session in Google Account → Security → Your devices. Deleting local files does not invalidate copies in backups or snapshots.
