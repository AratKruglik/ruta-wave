# 02. Architecture of the Swift version

Everything in this document is a **[decision]** unless labelled otherwise.

## 1. Key decisions

| Question | Decision | Rationale |
|---|---|---|
| Interface | SwiftUI; AppKit only where SwiftUI falls short (menu bar, Dock menu, fine window control) | user's choice: fully native UI |
| Minimum macOS | 14 | `@Observable` macro, mature `NavigationSplitView` |
| Language and concurrency | Swift 6, `async/await`, actors for networking and the player | no third-party reactive libraries |
| Data | the site's InnerTube API with the user's cookies | the same source the site and the original use |
| Sign-in | Google's page in a visible `WKWebView` | the password never passes through our code |
| Playback | hidden `WKWebView` + JS bridge | see section 3 |
| Settings | `UserDefaults` / `@AppStorage` | replaces `electron-store` |
| Secrets | Keychain | session cookies, Last.fm keys |
| Dependencies | none at the start | everything needed is in the SDK |
| Build | XcodeGen `project.yml` (generates `Redwave.xcodeproj`, not committed) + local Swift packages for modules | modules are tested separately with `swift test` |
| Distribution | DMG file outside the App Store | user's decision; see [03](03-roadmap.md#stage-8-building-the-dmg) |
| Sandbox | off; Hardened Runtime on | the sandbox is only required for the App Store; Hardened Runtime is a notarization prerequisite |

## 2. Modules

```
Redwave.app
├─ App            — entry point, scenes, routing, DI
├─ UI             — SwiftUI screens and components (for now lives in `App/`; extraction is decided at stage 4)
├─ PlayerEngine   — hidden WKWebView, JS bridge, player state
├─ InnerTube      — HTTP client, authorization, parsers, models
├─ Auth           — sign-in window, cookies, Keychain, session state
├─ SystemKit      — Now Playing, media keys, notifications, menus, hotkeys
├─ Plugins        — plugin protocol, registry, built-in plugins
└─ AppSettings    — typed settings on top of UserDefaults
```

Dependencies point downwards: `InnerTube → Auth`, `PlayerEngine → Auth`,
`Plugins → PlayerEngine, InnerTube, AppSettings`, `SystemKit → PlayerEngine, AppSettings`.
`InnerTube` and `PlayerEngine` do not know about each other; `Auth` and `AppSettings` are leaves.

## 3. Why audio goes through a hidden WKWebView

The alternative is to obtain direct audio stream URLs and play them with
`AVPlayer`. It was rejected:

1. Stream URLs are protected by a signature computed by YouTube's player code;
   the algorithm changes with player updates. It needs a JS interpreter and
   constant maintenance (in the original, `youtubei.js` does this).
2. Streams increasingly require a PoToken (in the original, `bgutils-js`),
   which is also generated by Google's code.
3. Bypassing these mechanisms directly violates YouTube's terms; with the site
   in a web view the user listens exactly as they would in a browser.
4. Premium, ads for free accounts, quality and listening statistics all work in
   the web view without any code of ours.

Consequences we accept:
- audio effects (equalizer, compressor, crossfade) are only possible through
  Web Audio inside the page, not through `AVAudioEngine`;
- the web view uses memory (roughly 150–300 MB);
- the page may change its structure — the bridge is isolated in one JS file.

## 4. PlayerEngine

### 4.1. Web view

- One `WKWebView` at a time. It is **recreated** when the session switches between
  guest and signed-in, and playback stops. A guest uses `WKWebsiteDataStore.nonPersistent()`
  so leftover `default()` cookies never reach a guest page; a signed-in session uses
  `.default()`, and the Keychain cookies are restored into it when it holds no `SAPISID`.
  `PlayerEngine.start(_:)` does this, and the App tears the view down as soon as sign-out starts (the wipe may already be running).
- It must be **attached to a window**, otherwise WebKit suspends timers and
  media: `PlayerHost` (App) puts it in a 1×1 container `NSView` with `alphaValue = 0`
  inside `PlayerWindow`, a borderless 1×1 window the app delegate creates once at launch
  (not restorable, not in the Window menu, ignores the mouse), and
  `preferences.inactiveSchedulingPolicy = .none`. The same hidden window runs the
  session-driven `start`/`stop`, so playback does not depend on which app windows are
  open: verified by hand with only the debug window open, after Close All, and with the
  app hidden. Background audio with the screen locked remains manual check MC-1.
- It must stay **re-parentable**: a later music video mode or picture-in-picture
  ([#12](https://github.com/AratKruglik/yt-music-mac/issues/12)) moves it into a visible container without reloading the page or
  interrupting playback. The stage 3 design (#13) must not rule this out; whether
  WebKit pauses media while the view is briefly detached is checked when video
  mode is picked up (risk 4 in [05](05-risks-and-scope.md)).
- `WKWebViewConfiguration`:
  - `mediaTypesRequiringUserActionForPlayback = []` — audio autoplay;
  - `websiteDataStore` — `nonPersistent()` for a guest, `.default()` when signed in (above);
  - `applicationNameForUserAgent = SignInRules.safariApplicationName` — the same Safari identity as the sign-in window;
  - a `WKUserScript` with the bridge, injected `atDocumentEnd`, main frame only.
- A guest loads `https://music.youtube.com/watch?v=<id>&list=<playlistId>`. Signed-in playback always loads
  `https://music.youtube.com/signin?action_handle_signin=true&authuser=<authUserIndex>&next=<encoded /watch?...>`,
  index 0 included: the site ignores `authuser` on `/watch` and keeps the last account it switched to (MC-8, 2026-11-19).
  IDs must match `^[A-Za-z0-9_-]{1,64}$`, otherwise nothing is loaded.
- **Navigation lock.** The view holds the Google-wide session, so the main frame
  may only load `https://music.youtube.com` (plus hosts that stage 3 proves it
  needs; `PlayerRules` currently allows only `music.youtube.com`, every cancelled host is
  logged for MC-7). Anything else is cancelled in `decidePolicyFor`; a user-clicked link is
  dropped (opening it in the browser is later work); `createWebViewWith`
  returns `nil`. `SignInView.swift` follows the same pattern. This matters once the
  view becomes visible and clickable (video mode, [#12](https://github.com/AratKruglik/yt-music-mac/issues/12)),
  and keeps the privacy rule that the app sends data only to Google
  ([00](00-prd.md)) true before that.
- **Bridge trust.** The `player` message handler accepts a message only when
  `frameInfo.isMainFrame` and the origin is https `music.youtube.com`. Message
  bodies are untrusted input, and a URL taken from a message is never opened.
  `evaluateJavaScript` runs only while the host is `music.youtube.com`; 3.1 has no Swift to JS call, and 3.2 adds
  commands through `callAsyncJavaScript` with arguments (no string building), guarded by that check. The bridge
  stays in the page world: an isolated `WKContentWorld` would break the
  `#movie_player` methods. Stage 3 tests that a foreign-host navigation is
  cancelled and a non-main-frame or foreign-origin message is dropped.

### 4.2. JS bridge

A single `Resources/bridge.js` file in the `PlayerEngine` target. It:
- waits for the site player to appear (the `#movie_player` and `ytmusic-app` elements) **[known]**;
- subscribes to events from the player and the `<video>` element
  (`play`, `pause`, `timeupdate`, `volumechange`, `seeked`, `loadedmetadata`);
- sends events to Swift through `window.webkit.messageHandlers.player.postMessage(JSON.stringify(...))`, always a string of at most 256 KiB
  (`ready`, `song` with the `videoDetails` and `microformat` of `getPlayerResponse()`, `playback {paused, time}`, `time {time}`);
  Swift drops anything that is not a trusted-origin, well-formed message;
- receives commands through `window.__bridge.run(action, args)`. `__bridge` is frozen and non-configurable, and `run` looks
  the action up in a frozen table of named operations (never an arbitrary method name) and resolves to `true` or `false`;
- pushes `volume`, `like`, `repeat`, `shuffle`, `queue` (one debounced push source: the queue store's `subscribe`, posted only
  when the projection changes, at most 500 rows), `ad` and `error {kind: "unavailable"}` (checked from `playabilityStatus`
  before the `videoDetails` guard, and also posted when the page leaves `/watch` before a song arrives there: a missing
  video id makes the page drop back to the home screen with no playability error, so the requested id is read from the
  navigation entry, which keeps the URL that was loaded). `song` is not posted while an ad shows.

Site player methods **[presence verified on the live page, MC-5, 2026-11-19]**: `playVideo()`,
`pauseVideo()`, `nextVideo()`, `previousVideo()`, `seekTo(sec)`, `setVolume(0…100)`,
`getVolume()`, `mute()`, `unMute()`, `getCurrentTime()`, `getDuration()`,
`getPlayerResponse()`, plus `stopVideo()`, `loadVideoById()`, `setShuffle()`, `setLoop()`,
`isMuted()` and `getPlayerState()`. Getters were called and returned plausible values; methods with
side effects were only checked to exist.

Page internals added in 3.2 **[reference-only: taken from pear-desktop, not yet probed live]**. Each is behind a named
bridge operation that returns `false` when the path is missing, and Swift logs the refusal. Status after the owner's
Web Inspector probe replaces "reference-only" with "verified presence <date>" or "unreachable":

| Item | Path | Status |
|---|---|---|
| next / previous | click `.next-button` / `.previous-button` on `ytmusic-player-bar`, fallback `nextVideo()` / `previousVideo()` | reference-only |
| volume write | `ytmusic-player-bar.updateVolume(0…100)`, fallback `setVolume` | reference-only |
| shuffle / repeat | `ytmusic-player-bar.queue.shuffle()` / `onRepeatButtonClick()`, fallback a click on the button | reference-only |
| shuffle, repeat read | `#queue.queue.store.store.getState().queue.{shuffleEnabled, repeatMode}` | reference-only. Whether shuffle is a mode or a one-shot reshuffle is unknown |
| like read | `like-status` attribute on `#like-button-renderer` | reference-only |
| queue read | `#queue.queue.store.store.getState().queue.items` and `.subscribe`, fallback `#queue.queue.getItems()` re-read on `videodatachange` | reference-only |
| queue edit | `#queue.dispatch` with `SET_INDEX`, `REMOVE_ITEM`, `MOVE_ITEM`, `ADD_ITEMS` | reference-only. Whether `SET_INDEX` starts playback is unknown |
| enqueue | `ytmusic-app.networkManager.fetch('/music/get_queue', ...)` then `ADD_ITEMS` | reference-only. If unreachable the command is refused |
| ad | `ad-showing` / `ad-interrupting` class on `#movie_player` | unknown (general YouTube knowledge) |
| unavailable | `getPlayerResponse().playabilityStatus.status !== 'OK'`; a missing id instead leaves `/watch` for `/` | missing id verified (MC-E); non-OK status reference-only |

The fallbacks "attribute observer for shuffle/repeat" and "`getPlayerResponse().videoDetails` vs the queue's selected row for ads" are not implemented.
The like write does not use the page: it goes through InnerTube `rate` (`PlayerEngine.rate`, set by the app).

### 4.3. Contract with Swift

Mirrors the original's `peard:*` channels
(see [01](01-reverse-engineering.md#44-player-control)).

```swift
enum PlayerCommand {
    case play, pause, togglePlay, next, previous
    case seek(to: TimeInterval), skip(by: TimeInterval)   // skip, not seek(by:): Swift cannot match two cases that differ only by label
    case setVolume(Double)                                // 0…1, clamped; NaN refused
    case toggleMute, toggleShuffle, cycleRepeat
    case setLike(LikeStatus)                              // signed-in only, through PlayerEngine.rate
    case playQueueItem(index: Int)
    case enqueue(videoId: String, playNext: Bool)
    case removeQueueItem(index: Int)                      // the current item is refused
    case moveQueueItem(from: Int, to: Int)
    case load(videoId: String, playlistId: String?)
}

enum PlayerEvent {
    case ready
    case songChanged(SongInfo)
    case playbackChanged(isPaused: Bool, elapsed: TimeInterval)
    case timeChanged(TimeInterval)
    case volumeChanged(volume: Double, isMuted: Bool)     // 0…1
    case likeChanged(LikeStatus)
    case repeatChanged(RepeatMode)
    case shuffleChanged(Bool)
    case queueChanged([QueueItem])
    case adChanged(Bool)
    case error(PlayerError)   // pageLoadFailed, playerTimeout, unavailable(videoId:), contentProcessCrashed, signInRequired
}

struct SongInfo: Equatable, Sendable {
    var videoId: String
    var title: String          // cleaned, see the rules below
    var artist: String
    var album: String?
    var artworkURL: URL?
    var duration: TimeInterval
    var elapsed: TimeInterval
    var isPaused: Bool
    var playlistId: String?
    var url: URL
}
```

Stage 3.2 completes the contract. There is no `seeked` event (the bridge turns `seeked` into `timeChanged`).
Commands are ignored, with a log line and no error, while the player is not started or not ready; while an ad plays, `next` and the
seeks are refused. The only refusal that emits an error is `setLike` without a signed-in session. `SongInfo.elapsed` and `isPaused` are a snapshot
taken at `songChanged`; the live values are `PlayerEngine.elapsed` and `isPaused`, so a 4 Hz time update never invalidates observers of `song`.
`events()` fans out to every caller, each with a 64-event buffer.

`PlayerEngine` is a `@MainActor @Observable` class: it holds the current state
for the UI and vends an `AsyncStream<PlayerEvent>` for plugins and `SystemKit`.

Rules ported from the original **[bundle]**:
- artwork is the largest thumbnail, URL without the query, with a fallback;
- the title is cleaned with the same regular expressions
  (listed in [01](01-reverse-engineering.md#45-the-songinfo-track-model));
- position updates do not rebuild `SongInfo`, they only change `elapsed`.

### 4.4. Queue

The queue belongs to the page (as in the original). Swift reads it through the
bridge and displays it; changes (add, remove, move, jump) are sent as commands.
`PlayerEngine.queue` is a display mirror that each `queueChanged` replaces wholesale, so it cannot
drift from the player. It holds the main queue only (no Autoplay section) and at most 500 rows: the page trims, and Swift
rejects a larger message, and any message with one invalid row, because dropping a row would shift every later index.
A queue command carries the row's index together with its `videoId` and `playlistSetVideoId`; the page refuses the
operation when the row at that index no longer matches.

**Recovery.** `PlayerEngine` keeps an in-memory snapshot (target track, position without ad time). A content process crash,
a load failure or no `song` within 15 s (a Swift timer, because a JS timer dies with the process) reloads the target through the same URL as
`load`, at most twice, then gives up silently; the last `error` stands. After a crash the same track is re-announced
with `songChanged` and seeked back to the snapshot position. Skipping an unavailable track is left to the UI.

## 5. InnerTube

Everything in this section is **[known]** from open projects and is verified at stage 2.

### 5.1. Requests

- `POST https://music.youtube.com/youtubei/v1/<endpoint>?prettyPrint=false`
- The body contains `context.client`: `clientName: "WEB_REMIX"`, `clientVersion`
  (taken from the page, key `INNERTUBE_CLIENT_VERSION` in `ytcfg`), `hl`, `gl`.
  Every launch refreshes the version in the background with an anonymous `GET /`; requests never wait for it.
  The fallback order is the discovered value, then the cached one (`UserDefaults`), then the built-in one.
- Headers of an authorized request:
  - `Cookie` — session cookies;
  - `Authorization: SAPISIDHASH <ts>_<sha1("<ts> <SAPISID> <origin>")>`;
  - `X-Origin: https://music.youtube.com`, same for `Origin`;
  - `X-Goog-AuthUser: <authUserIndex>` — the selected account, 0 by default.
- Headers of a guest request: `Content-Type`, `Origin`, `X-Origin`, `User-Agent`, and `X-Goog-Visitor-Id` once known;
  never `Cookie`, `Authorization` or `X-Goog-AuthUser`. `visitorData` comes from `responseContext.visitorData` of a
  guest response (the latest valid value wins), is kept in memory only and is reset on sign-in and sign-out.
- `GET https://music.youtube.com/getAccountSwitcherEndpoint` — same headers, no body; the JSON may start with the
  XSSI prefix `)]}'`, which is optional. The app always sends it with `X-Goog-AuthUser: 0`.

### 5.2. Endpoints

| Endpoint | Purpose |
|---|---|
| `browse` | home (`FEmusic_home`), explore (`FEmusic_explore`), library (`FEmusic_library_landing`, `FEmusic_liked_playlists`), history (`FEmusic_history`), album (`MPREb…`), artist (`UC…`), playlist (`VL<id>`) |
| `search` | search with filters (songs, albums, artists, playlists) |
| `music/get_search_suggestions` | search suggestions |
| `next` | "up next" queue, radio, related tracks, lyrics identifier |
| `like/like`, `like/dislike`, `like/removelike` | ratings |
| `playlist/create`, `playlist/delete`, `browse/edit_playlist` | playlist management |
| `subscription/subscribe`, `subscription/unsubscribe` | artist subscription |
| `feedback` | remove a search-history entry or a History row by `feedbackToken` |
| `account/account_menu` | account name and avatar, session check |
| `GET /getAccountSwitcherEndpoint` | the session's Google accounts; `authuser` comes from `signinUrl` (brand accounts are skipped) |

Mutations are signed-only (a guest call throws `signInRequired` before any request) and are never retried. Feedback tokens and `playlistSetVideoId` values are bound to the account that fetched them: send them only with that account's credentials, and cancel any delayed send (Undo window) on sign-out or account switch.

### 5.3. Module layout

```
InnerTube
├─ InnerTubeClient (actor)  — builds, signs and runs requests, follows `continuation`
├─ Endpoints                — typed request descriptions
├─ Parsers                  — JSON → models; one file per page type
└─ Models                   — Song, Album, Artist, Playlist, Shelf, SearchResults, Page<T>
```

InnerTube responses are deeply nested "renderer" structures that change often.
So parsers do not use wholesale `Codable`; they walk a `JSONValue` and tolerate
missing fields: an unknown block is skipped instead of failing the page. This is
the only place that knows Google's format.

## 6. Auth

1. Without a session the app shows the guest screen; sign-in opens in a sheet behind a "Sign in" button.
   Cancel wipes the `WKWebsiteDataStore` (not the Keychain) and returns to the guest. Sign-out also leads to the guest.
   `.keychainUnavailable` offers "Try again" and "Continue without signing in" (this launch only; the Keychain entry is kept, but cancelling a later sign-in still wipes the web view store).
   The sign-in page is the same `ServiceLogin…continue=music.youtube.com` URL the original uses.
   An HTTP 401 on a signed-in request wipes the session (WebKit store, then Keychain) and shows the guest screen
   with "Your session expired. Sign in again." and the sign-in sheet; there is no cookie re-read and no retry (2.1).
   Other failures still show the error with Retry / Sign out.
   Besides exact Google hosts, only `accounts.<google domain>/accounts/SetSID` is allowed, for domains from an embedded snapshot of google.com/supported_domains (taken 2026-11-18); refresh the snapshot manually when a regional sign-in hangs.
2. After the redirect back to `music.youtube.com`, cookies are read from
   `WKHTTPCookieStore`; at least `SAPISID`, `__Secure-3PAPISID`, `SID`, `HSID`,
   `SSID` are needed **[known]**.
3. Cookies are stored in the Keychain and supplied to `InnerTubeClient`.
   A signed-in player web view uses the same `default()` website data store. On sign-in the Keychain cookies are
   restored into it when it has no `SAPISID`. A guest player uses its own `nonPersistent()` store.
4. Sign-out: clear the Keychain and `WKWebsiteDataStore`.
5. `AuthSession.State.isSignedIn` is the single source for "hide an account-only action or offer sign-in";
   `.signedOut` means guest. Consumers: 2.1, 2.4, 3.2, 4.1, 4.5, 4.6.

## 7. UI

The look is fixed in [07-designbook.md](07-designbook.md) and the behaviour of every part in
[08-ui-spec.md](08-ui-spec.md); this section keeps only the structure.

The window is a `NavigationSplitView`:

```
┌───────────────┬──────────────────────────────────────────┐
│ Sidebar       │  Content (NavigationStack)               │
│  Home         │   Shelves → cards → album / artist /     │
│  Explore      │   playlist pages                         │
│  Library      │                                          │
│  ───────────  │                                          │
│  Playlists…   │                                          │
├───────────────┴──────────────────────────────────────────┤
│ Player bar: artwork, title, controls, position, volume, queue │
└──────────────────────────────────────────────────────────┘
```

Screens: Home, Explore, Library (playlists, songs, albums, artists), Search with
suggestions and filters, Album, Artist, Playlist, Queue (right-hand panel),
Lyrics, Settings (a separate `Settings` scene), Sign-in, Mini player (a separate
compact window).

Principles:
- every screen has an `@Observable` model with loading, data and error states;
- lists are `List`/`LazyVStack` with paging through `continuation`;
- images use `AsyncImage` plus `URLCache`; no separate library;
- accessibility: every control has a VoiceOver label, and all player controls
  are reachable from the keyboard.

## 10. Plugins

```swift
@MainActor
protocol Plugin: AnyObject {
    static var id: String { get }
    static var title: LocalizedStringResource { get }
    var isEnabled: Bool { get set }

    func start(context: PluginContext) async
    func stop() async
    @ViewBuilder var settingsView: AnyView? { get }
}

struct PluginContext {
    let player: PlayerControlling           // commands and current state
    let events: AsyncStream<PlayerEvent>    // equivalent of subscribing to SongInfo
    let innerTube: InnerTubeClient
    let settings: PluginSettings            // the plugins.<id>.* key space
    let injectScript: (String) async -> Void // for plugins that run inside the page
}
```

Plugins are built into the app and toggled in settings; there is no dynamic
loading of third-party code. The list and the split across stages is in
[04-plugins.md](04-plugins.md).
